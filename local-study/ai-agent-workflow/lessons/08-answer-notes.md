# 理解检查参考答案

建议先完成每课的问题再阅读。本文件用于自查，不代表已经评估你的掌握程度。

## 第 1 课

1. 外部工具必须在当前用户权限内运行。Frontend service 接收 Session 并做身份 / 资源权限检查；直接调用内部 Backend 容易绕过这道边界。
2. 检查写操作是否触发了正确的 Fusion 失效、计算依赖是否建立、客户端是否订阅了对应状态。写数据库成功并不自动证明缓存正确。
3. 用当前注册与调用链判定实际行为，记录提交版本。计划说明意图，索引帮助导航，两者都需要源码验证。

## 第 2 课

1. 作者映射包含作者标识和对应 mention；对话正文包含消息及其作者表示。
2. 三个事实是计划周五发布、权限测试是前置条件、不通过则延期。
3. “周五一定发布”可以是完全合法的 JSON。结构检查不能检查事实与条件是否被改变，需要原文证据和内容评估。
4. `SanitizeSummary` 构造允许的作者 mention 集合，后续 markup 过滤移除未知作者 / 非 Author mention，并限制数量。

## 第 3 课

1. `await` 只描述进程内异步控制流，不自动持久化调用栈。持久化 Flow 重新读取状态再执行恢复方法。
2. `LastSummaryEndLid` 用于识别上次处理位置；模型已返回但该字段尚未提交时崩溃，恢复后可能再次生成。
3. inbox diff 与 Flow 状态可以参与同一次数据库操作；外部 HTTP 请求或另一独立服务的提交不在该事务内。

## 第 4 课

1. 工具列表描述能力，调用时还要验证身份、资源权限及管理员权限等业务条件。
2. Session 是授权上下文，应由可信宿主和认证机制建立；模型自由选择身份会把普通参数变成权限升级入口。
3. 工具错误是一个执行步骤的结果；任务成功需要验证最终回答或业务目标。即使每次工具调用都返回 200，答案也可能错误或不完整。

## 第 5 课

1. 可先读 `ShouldLimitMentionsToKnownAuthors` 或 `ShouldLimitDetectionToLatestEntries`，因为它们验证确定性应用行为，而非对模型能力作主观评价。
2. JSON / schema / 字段校验验证结构；事实评估用输入证据检查是否遗漏、歪曲或捏造。
3. 同时观察外部调用次数、去重键、业务写入数和持久化状态。只断言最终摘要存在，会漏掉重复写入或重复计费。

## 第 6 课

1. 风格检查判断代码约定，业务测试判断确定性规则，模型评估判断内容质量。它们有不同的失败来源，不能互相替代。
2. Hook 要由兼容的运行环境读取并执行。某个客户端的配置存在，不证明另一个编辑工具或 CI 已接入。
3. 技能也是会过时的工程资产。错误路径会使关键检查没运行，其他技术栈例子可能误导修复方案；要保留检查目的，按当前实现验证。

## 最后用三句话解释

- 摘要组件负责把模型请求与结果处理封装成业务能力。
- Workflow 负责在明确的业务条件下执行、保存进度和再次调度。
- Agent 让模型选择下一步，但宿主仍必须控制工具、权限、预算和停止条件。
