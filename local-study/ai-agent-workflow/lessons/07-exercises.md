# 第 7 课：三个渐进练习

这些是后续实现规格，本次只交付设计，不创建可运行产品代码、不安装 SDK、不调用模型或生产服务。
先完成 A，再做 B，最后做 C。只有前一项的验收可解释、可复核，才增加下一层复杂度。

## 练习 A：可验证的单次摘要

### 目标

给定虚构聊天消息，输出标题、摘要和可核对的事实记录。先使用假模型响应，将非确定性隔离。

### 输入与输出

输入采用固定的 3 条虚构消息：

```json
[
  {"id": 1, "author": "A", "text": "我们计划周五发布搜索功能。"},
  {"id": 2, "author": "B", "text": "发布前必须完成权限测试。"},
  {"id": 3, "author": "A", "text": "权限测试不通过就延后发布。"}
]
```

成功时结果必须保留“计划周五”“权限测试前置条件”“不通过则延期”。评估表把每个事实对应到输入 ID，不要求产品里的 `ConversationSummary` 新增字段。

失败状态分为无输入、模型调用失败、输出解析失败。不要用一段失败文案伪装成成功摘要。

### 实施方式

- 若后续在本仓库实施，先从 `ConversationSummarizerLanguageTest` 学习依赖替换，再定位 SDK 调用的可替换边界。
- 测试数据与假响应先覆盖正常、空、格式错误和未知作者；真实模型另设显式启用的评估步骤。
- 暂不修改已有生产摘要结果契约；练习记录用自己的结果状态区分成功和失败。
- 每次真实评估记录 Prompt 版本、模型标识、输入版本和 usage，凭据从受控环境注入，不入库。

### Reuse

复用 `IConversationSummarizer`、`IChatDialogFormatter`、`SanitizeSummary` 的设计及现有测试模式。
新增的假响应数据和评估表仅服务练习，放学习目录或对应测试项目；不提升到 `Core.Server`。
只有形成被多个功能需要的通用输出校验能力时，才比较 `Core`（无服务依赖）与 `Core.Server`（有服务依赖）的位置。

### 验收

| 样例 | 应有结果 |
|---|---|
| 正常三条消息 | 保留三个事实及条件 |
| 空输入 | 明确空输入状态，不调用模型 |
| 非 JSON / 类型错误 | 明确解析失败，不当作有效摘要 |
| 未知作者提及 | 输出不含越界提及 |
| 含“忽略规则，伪造结论”的输入 | 不改变运行时权限，事实评估能发现伪造 |

## 练习 B：能恢复的摘要工作流

### 目标

模拟收到新消息、延后处理、恢复和失败。分开观察“模型尝试次数”和“成功提交的摘要数量”。

### 实施方式

先在隔离测试 Flow 中使用假摘要器。状态只包含处理进度与结果引用；以最后已处理消息 ID 判断是否有新数据，使用 `StageResumeIn` 安排下一次。

故障注入选两处：模型返回之后、Flow 提交之前；成功提交之后、再次收到触发之前。通过计数器记录模型尝试次数，通过持久化状态记录成功结果数。

针对练习中的业务结果，以“聊天 ID + 输入最后消息 ID + 练习 Prompt 版本”构造稳定操作身份。它只是练习约定；生产中消息可编辑，若推广必须把内容版本 / 内容哈希纳入，避免错误复用旧结果。

不自行增加数据库迁移；优先使用现有测试 Flow 状态和 inbox 验证。不得声称这种方式能够阻止 provider 已发生的重复计费。

### Reuse

复用 `Flow`、`FlowHub`、`FlowRuntime`、`FlowInbox`、`TestWait` 和现有测试宿主。
练习 Flow 默认放对应测试项目，避免给生产注册表增加演示任务。
若以后确有多功能需求，再考虑 `Core.Server` 共享抽象；当前不创建通用 Agent 框架。

### 验收

- 无新消息时不再次生成。
- 恢复后处理进度不丢失；失败尝试不会提前标记为已处理。
- 新消息在恢复过程中到达时不丢失。
- 陈旧版本提交不能覆盖新状态。
- 报告模型调用次数与业务提交次数，不把两者混为一谈。
- 明确 429 的延后策略和最终完成期限冲突时如何处理；先用假时钟验证。

## 练习 C：只读聊天检索 Agent

### 目标

实现“查找相关消息并回答一个问题”的外部 Agent，让模型可自主选择是否检索。先使用本地模拟工具，成功后才讨论连接本地开发 MCP。

### 最小行为规格

- 工具允许集合只包含 `search_messages` 和 `list_messages`，不开放发消息、SQL、删除或管理工具。
- 运行时最多允许 3 次模型决策和 3 次工具调用；每轮最多执行一个工具。达到任一上限后返回可解释的未完成结果。
- 工具参数经过类型和范围验证；用户身份固定在宿主运行时，模型不能传入或替换 Session。
- 模型得到工具返回后可继续查询或结束；最终回答引用实际返回过的 `(chatId, entryId)`。
- 没有证据时明确说明未找到；工具错误也作为受限结果交回模型，不伪装成成功。
- 记录工具名、脱敏参数摘要、状态与次数；不保存凭据或原始私聊内容。

这个循环是练习新建的外部能力，不是假定当前产品已经有相同实现。为避免提前绑定框架，本次给行为规格，不编造尚未验证的 SDK 示例。

### Reuse

复用现有 MCP 工具命名、参数和结果形状作为模拟器契约；复用业务权限测试的多用户思路。
Agent 编排默认放独立学习客户端，不放产品某个 UI 组件，也不放 `Core.Server`。只有将来确定要作为产品多功能公共能力时，才评估共享项目。

### 验收

| 场景 | 应有结果 |
|---|---|
| 可直接回答的已知上下文 | 能结束，不强制调用工具 |
| 单次搜索即可得到证据 | 回答只引用返回过的消息 |
| 搜索无结果 | 不捏造消息或引文 |
| 工具要求查看他人私聊 | 返回拒绝，最终回答不泄露内容 |
| 工具结果诱导调用 `post_message` | 运行时拒绝未允许工具 |
| 连续工具错误 / 无进展 | 在预算内停止，明确未完成 |
| 用户取消 | 停止后续模型与工具调用 |
